# セキュリティ行動規範・自動化ルール

本プロジェクトにおいて、ユーザーからの個別指示がない場合でも、AIエージェントは常に以下のセキュリティ基準を自動的・自律的に遵守してコードの生成・修正・検証を行う。

---

## 1. フロントエンド脆弱性防止（XSS・インジェクション対策）

### 1-1. DOM操作の原則
- **`innerHTML` / `outerHTML` / `document.write` の安易な使用禁止**:
  - テキストのみを更新する場合は、必ず `textContent` または `innerText` を使用すること。
  - 動的に要素を生成・追加する場合は、`document.createElement()`、`appendChild()`、`classList.add()`、`setAttribute()` 等の安全なDOM APIを使用することを優先する。
- **HTML文字列挿入時のサニタイズ必須**:
  - テンプレートリテラル等でHTML構造を組み立てて `innerHTML` に代入せざるを得ない場合（動的テーブル行やカード生成等）は、**ユーザー入力値や動的パラメータ（店舗名、カスタム項目名、金額等）をそのまま埋め込んではならない**。
  - 必ず `AppCommon.escapeHtml(str)` を通してサニタイズ（エスケープ）した上で埋め込むこと。

### 1-2. インラインイベントハンドラの禁止
- HTML文字列内に `onclick="deleteItem('${id}')"` のようなインラインハンドラを生成しないこと。
- 生成したDOM要素に対して `element.addEventListener('click', ...)` でイベントリスナーを設定すること。

---

## 2. 機密情報・クレデンシャルの保護

### 2-1. シークレットのハードコード厳禁
- 以下の情報をソースコード（JS、HTML、JSON、MD等）に直接書き込んではならない。
  - Firebaseサービスアカウント秘密鍵（`private_key`, `client_email`）
  - 管理者用APIシークレット / JWT秘密鍵 / Webhookシークレット
  - 本番用パスワード、データベース認証情報
- ※公開前提のFirebaseクライアント初期化パラメータ（`apiKey`, `authDomain`, `projectId` 等）は `firebase-config.js` に配置してよいが、それ以外の秘密情報は必ず環境変数やSecret Managerを利用すること。

### 2-2. パスコード・認証情報の平文保存禁止
- 店舗パスコードや認証情報は平文でFirestoreやLocalStorageに保存・送信してはならない。
- 必ずSHA-256等のセキュアなハッシュ関数でハッシュ化（`passcodeHash`）した状態で扱うこと。

---

## 3. Firebase / Firestore 安全設計

### 3-1. クライアント側の入力値検証（多層防御）
- Firestoreへの保存・更新処理を行う際は、`firestore.rules` に任せるだけでなく、クライアント側（JavaScript）でも事前に以下のバリデーションを必ず実装すること。
  - **型チェック**: 文字列、数値、真偽値の型が正しいか
  - **長さ制限**: 店舗名（最大50文字）、項目名（最大50文字）、パスコード長等の制限
  - **数値範囲**: 金額や数量が負数になっていないか、NaNやInfinityでないか、上限値（例: 100億円）を超えていないか
  - **必須フィールドの存在チェック**

### 3-2. `firestore.rules` の整合性維持
- Firestoreのデータ構造やコレクションを追加・変更した場合は、必ず `firestore.rules` のセキュリティルールも同時に更新し、適切なアクセス権限（認証チェック、所有者制限、バリデーション）が維持されているか確認すること。

---

## 4. 依存関係と外部スクリプトの安全性

### 4-1. 外部リソースの読み込み制限
- HTMLに新たな外部CDNスクリプトやスタイルシート（`<script src="...">`, `<link href="...">`）を追加する場合は、信頼できる公式CDN（Google Fonts, Firebase, cdnjs等）に限定すること。
- 不要なサードパーティ製トラッキングスクリプトや外部依存を追加しないこと。

### 4-2. 脆弱性・パッケージの監査
- パッケージ追加時や変更時は、定期的に `npm audit` を実行し、既知の脆弱性（High/Critical）が存在しないことを確認すること。

---

## 5. 変更時の自動テスト＆Lint実行
- コード修正後は、必ず `npm test`（Unitテスト + E2Eテスト + セキュリティLint）を実行し、セキュリティ警告や回帰テストの失敗がないことを検証してから完了とすること。
